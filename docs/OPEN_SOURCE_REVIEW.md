# Open-source release review

Prepared 2026-11-05 against local commit `3f7286c` and the launch-preparation working tree. This is a source/readiness review, not a penetration test or permission to publish. No visibility, remote configuration, credential, hosted database, release or package publication was changed.

## Audit scope and method

- Inspected tracked source/configuration, all locally available branches/remotes/tags and reflog-reachable history: **7 commits and 422 unique Git blobs** before these documentation changes. Remote-tracking refs are only the locally available snapshot; no claim is made about unseen remote refs.
- Scanned text blobs for OpenAI/Supabase/GitHub/AWS key formats, private keys, JWTs (including service-role payloads), password-bearing database URLs and sensitive literal assignments. Findings were reported by location/category only; no secret values were printed. This was a targeted pattern/manual review, not a maintained full secret-scanner certification.
- Additionally scanned **105 unreachable local blobs** for credential patterns; no matches. These local objects are not normally pushed as reachable history, but are relevant if someone shares an entire `.git` directory. No history was rewritten or garbage-collected.
- Reviewed environment tracking, production URL patterns, fixture provenance, seed/migration content, dependency license metadata and PNG metadata chunks. PNGs contain no text/EXIF chunks; this does not establish artwork ownership or exclude information encoded into pixels.
- Ran `npm audit --json` and a separate `npm audit --omit=dev --json`. These query the public npm advisory service; results are time-specific.
- No hosted GitHub Actions logs/artifacts/caches, GitHub security alerts, PR-only refs, forks, old clones, external backups or production records were accessed. GitHub CLI/private API access was unavailable in this environment. Owner review of those surfaces is required before publication.

## CI and contribution controls prepared

`.github/workflows/ci.yml` runs `lint`, `typecheck`, `tests` and `build` as isolated matrix jobs on GitHub-hosted Ubuntu with Node 24. Checkout/setup-node are pinned to verified full upstream commit hashes; checkout does not persist credentials. The workflow uses `pull_request` rather than privileged `pull_request_target`, read-only contents permission, blank service credentials, mocked AI and no hosted integration opt-in. It has no deployment step, secret reference, environment approval bypass, artifact upload or dependency/build cache. A 15-minute job limit bounds accidentally slow work; it is not a complete defense against malicious dependency code.

The workflow has not been pushed or executed on GitHub. Validate its first run after an owner-approved push, before requiring its check names. Official guidance: [secure Actions use](https://docs.github.com/en/actions/reference/security/secure-use).

## Exact GitHub settings for the owner

Do these manually after reviewing this patch; no setting below has been changed here. Interface names/availability can vary by account plan. Keep visibility private until all publication gates are resolved.

1. **Settings → Actions → General**: allow GitHub-owned actions needed by the two pinned action references; set default Workflow permissions to **Read repository contents and packages**; leave **Allow GitHub Actions to create and approve pull requests** off. Require approval for **all outside collaborators** before their fork workflows run, where available. Use GitHub-hosted ephemeral runners, not a privileged self-hosted runner. Keep write tokens and secrets withheld from fork PRs. Keep deployment workflows separate from untrusted PR code.
2. **Settings → Branches → Add branch protection rule**, branch pattern **`main`** (or an equivalent active branch ruleset): require a pull request, at least **one approving review**, dismiss stale approvals after new commits, require conversation resolution and passing status checks. Select the actual `lint`, `typecheck`, `tests`, `build` checks emitted by CI's first approved run; require the branch to be up to date. Disallow force pushes/deletions and include administrators/no routine bypass. An eligible reviewer other than the PR author is needed; establish that reviewer before enforcing a rule that would block all merges. Availability while private depends on the account plan. [Branch protection reference](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches).
3. **Settings → Advanced Security** (or Code security/analysis): enable dependency graph and Dependabot alerts, secret scanning and push protection where available. Review existing alerts and do a maintained full-history scan before release. Enable/test **Private vulnerability reporting** when supported for the public repository; verify the Security → Advisories reporting form and establish the private fallback before launch. [Private reporting reference](https://docs.github.com/en/code-security/how-tos/report-and-fix-vulnerabilities/configure-vulnerability-reporting/configure-for-a-repository).
4. **Settings → Secrets and variables → Actions / Environments**: verify CI needs **no service credentials**. Review old repository/organization/environment secrets and integrations privately; restrict any future production credentials to protected deployment environments with owner review. Do not copy them into this CI workflow. No secrets were read or removed here.
5. **Settings → Actions → General → Artifact and log retention**: choose a short retention such as **7 days**. Inspect all existing runs/logs/artifacts/caches, including historical workflows, before visibility changes; delete sensitive material only after owner-approved incident handling. No CI artifacts are uploaded by this patch. Do not upload `.next`, `.env*`, database exports or private browser captures later.
6. **Settings → General → Features**: enable Issues if desired and verify issue forms/PR template. Create `good first issue`, `help wanted`, `documentation`, `bug`, `enhancement`, and any relevant area labels labels manually. Review the category/moderation plan in [COMMUNITY.md](COMMUNITY.md#discussions-recommendation) before enabling Discussions; no issues, labels or Discussions are created by this patch. Confirm the default branch and repository description match the release state.
7. **Before any visibility change**: confirm license/assets, identity privacy, dependency advisory disposition, reporting contact, remote history/log review and local setup evidence. Then request a separate explicit owner approval for publication. Repository visibility, Git pushes, releases and credential rotations remain separate authorised actions.
